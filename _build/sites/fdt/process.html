How a Forward Deployed Tester engagement runs

Vendors' forward-deployed engineers deliver the AI. Nobody independently measures it. This is the process for that measurement.

  • Seven phases, five ledgers, one unit of work.
  • The two agents in this repo do the deterministic parts.
  • Plus how we work on the repo, so the next person or model can pick up where the last one stopped.

Why this process exists

The research behind the thesis found the same gap in every thread:

  • Palantir, OpenAI and Anthropic all field forward-deployed engineers whose success is "impact on the customer's goal".
  • No vendor publishes a pre-deployment baseline protocol.
  • No named role independently audits what an FDE delivered.
  • The rigorous studies (METR, DORA 2024) found effects that contradict the vendor claims.
  • MIT's "95% of pilots show no P&L impact" is mostly a story about absent baselines, not broken models.
How it goes today
  • The vendor defines "resolved".
  • The customer has no pre-AI numbers.
  • The pilot ends with a slide deck and a disputed tally.
→
With a Forward Deployed Tester
  • One unit of work is named up front; its pre-AI cost is frozen and signed.
  • The AI is scored on that unit across every rubric axis.
  • Tokens and infra are ledgered on that unit.
  • The verdict states its causal design and its limits.

Everything below is keyed on the unit of work: a ticket, a claim, a document, a pull request. Pick it in the first week or nothing later can be compared.

The seven phases

  • Each phase writes rows into one of the ledgers in the next section.
  • Each is runnable with no model at all.
  • Plates 44 and 45 do the deterministic work of phases 1 and 6; the rest is the redesign still ahead (see the progress log).
1

Discover

  • Map the workflow, define the unit of work, name the KPI owner on the customer side (usually missing).
  • Run the surface probes: the crawler (plate 44), API probes, log probes.
  • Output: a written unit-of-work definition and a findings baseline for the app as it stands.
rows → Baseline (surface), Findings
2

Baseline

  • Instrument the pre-AI workflow, or replay 30–90 days of historical records.
  • Freeze human time, error rate, throughput and cost per unit of work, with the KPI owner's signature.
  • Nothing downstream is valid without this row.
rows → Baseline
3

Golden set

  • Build the eval dataset from real traffic, PII redacted offline.
  • Labelled by the customer's own experts.
  • OpenAI's FDE "trajectories" practice, done independently of the vendor.
rows → Golden set (unit × label)
4

Eval cube

  • Rubric evals with a local open-weight judge, calibrated against a human-labelled slice, judge-bias mitigations built in.
  • Rubric axes × workflow steps × variants (model, prompt, retrieval, temperature).
  • Rotating one face must not silently degrade another; a regression gate watches every cell.
rows → Eval cube (unit × axis × step × variant)
5

Cost ledger

  • Tokens per unit of work per model, from the customer's own usage records; never estimated, the Claude tokenizer is not public.
  • Self-hosted infra measured under real concurrency.
  • Priced from vendored tables with their snapshot date printed.
rows → Cost (unit)
6

Pilot with a causal design

  • Shadow mode or A/B where possible; pre/post with stated limits where not.
  • The standardised regression suite (plate 45) runs on every change.
  • A quality regression is caught by a test, not by a customer.
rows → Outcome (unit)
7

Verdict and handover

  • Cost per verified outcome, confidence, go / no-go / conditions.
  • The harness stays behind, so the organisation re-runs the validation on every future change without us.
rows → Verdict (engagement)

The five ledgers

  • Everything the engagement produces is a row in one of five tables, keyed on the unit of work.
  • The existing SQLite schema (engagements, runs, findings, artifacts) is the substrate.
  • The ledgers are the next tables to add: the first work item of the redesign.
LedgerQuestion it answersKeyed on
BaselineWhat did this unit cost in human time, errors and money before AI?unit of work
Eval cubeHow does the AI score on every rubric axis, every workflow step, every model or config variant?unit × axis × step × variant
CostTokens by model, plus self-hosted infra under real concurrencyunit of work

Working rules for the repo

Four principles from the README, enforced by code where possible, and three gates every change passes.

  1. Deterministic first
    RuleEvery deliverable exists with LLM_PROVIDER=none; maybeLlm() guarantees the fallback. CI runs with the provider set to none.
  2. Local open-weight models only
    RuleassertLocalEndpoint() rejects any host that is not loopback, RFC 1918 or .local. There is no paid-provider code path.
  3. One agent, one folder, one owner
    RuleAgents never import from each other. Each has its own CLI, routes, tests and plate. Shared code lives in src/core only.
  4. No real names
    RuleNo client, product or colleague names in code, fixtures, docs or the progress log. The fixture estate is "Fabricated Shop" on shop.example.test.
  5. Gate 1 · typecheck
    npm run typecheck
    WhyStrict TypeScript with NodeNext resolution. The generated Playwright project is also compiled by the end-to-end test, so a generator that emits bad TypeScript fails here.
  6. Gate 2 · tests, no model
    LLM_PROVIDER=none npm test
    Why89 tests: parsers, locator tables, generators, reports, database, the endpoint guard, one real Chromium crawl, one end-to-end migration of the fixture estate.
  7. Gate 3 · CI on push and pull request
    cat .github/workflows/ci.yml   # Node 24, Chromium, typecheck, test
    WhyThe same two gates on a clean Ubuntu runner with Node 24. First run green on 2026-09-13.

The session loop

  • Sessions are short and models change between them; the only memory that survives is the repo.
  • Every session starts by reading the progress log and ends by writing to it.
  • CLAUDE.md makes this mandatory for any agent; for a person it is a habit.
sed -n 1,60p PROGRESS.md            # 1 · where things stand, newest day on top
                                    # 2 · take item 1 of "Open / next"
                                    # 3 · ...work...
npm run typecheck && LLM_PROVIDER=none npm test   # 4 · both gates
git add -A && git commit -m "..."    # 5 · snapshot, with the why
npm run progress                    # 6 · stamps today's header + measured snapshot at the top
                                    #     then fill in Done / Decided / Open by hand
What the snapshot measures. Commits, sync with origin, uncommitted files, typecheck, test counts, line counts, agent runs in the database. Numbers are exact; the narrative is written by whoever did the work.
If a session ended without the log. Backfill from git log --date=iso, file times, workspace/*/run.log and the runs table; mark the entry reconstructed; then start on the open items.

Risks the research surfaced, and the guardrail for each

Judge accuracy on hard cases is weak, open or closed
The verdict carries the judge's calibration score against the human-labelled slice and the human spot-check rate. Neither is hidden in an appendix.
Causal attribution is the hard part
Pre/post without a control is what the vendors do and why their numbers are disputed. Every Outcome row states the design used (pre/post, shadow, A/B) and its limits; the verdict repeats them.
The Claude tokenizer is not public
Cost for Claude comes from recorded usage, never from an estimate. Estimation is allowed only for models whose tokenizer is vendored.
Offline operation goes stale
Vendored price tables and pinned OTel conventions carry a snapshot date, and every report prints it.
Scope creep into governance and compliance
Crowded market, different buyers. Stay on measurement: baseline, eval, cost, outcome, verdict. Nothing else.

Command cheat-sheet

Everything you run in this repo, on one screen.

npm install && npx playwright install chromium
Once per machine. Chromium is only needed by plate 44.
npm run db:init
Creates data/forward-qa.db. Idempotent.
npm run agent:fdt -- --url <url> --org <slug>
Plate 44 against a running app. Report and infra land in workspace/<run_id>/.
npm run agent:sdet -- --src <abs dir> --org <slug>
Plate 45 against a legacy estate. MIGRATION.md is the work list.
npm start
REST API on port 8787: engagements, runs, findings, artifacts, report and migration routes, preview.
npm run typecheck && LLM_PROVIDER=none npm test
The two gates. Both must be green before a commit.
npm run progress
Stamp today's entry at the top of PROGRESS.md with measured numbers; -- --print shows them without writing.
npm run catalog
Rebuild index.html and agents/*.html from _build/content/*.json. Edit the JSON, never the HTML.
./scripts/setup-local-llm.sh
Optional: installs Ollama and pulls deepseek-r1:8b so summaries and TODO hints get a local model.
