Landing in a new environment

The Forward Deployed Tester

Point it at a running web app; it crawls, records findings and provisions a complete Playwright + MCP test project in one run.

Source: src/agents/the-forward-deployed-tester/  ·  Doc: docs/agents/the-forward-deployed-tester.md  ·  Tests: tests/the-forward-deployed-tester/

A new engagement starts and there is no test estate. This agent does the first week in one run: it launches a real Chromium through Playwright, walks every same-origin page it can reach from target_url, harvests the accessibility tree, writes severity-graded findings to the shared SQLite database, and leaves behind a runnable Playwright + Playwright MCP project — page objects, a smoke suite, a consoleErrors fixture, CI, a README and .mcp.json — plus report.md and report.json. In the 2026-09-11 04:32 run against a local three-page demo site it rendered 3 pages in 2.0 s, recorded 4 findings (2 medium, 2 low), derived 9 locators of which 8 are role-based, and wrote 11 files. It needs no model: with LLM_PROVIDER=none every deliverable is identical, and a local open-weight model only rewrites the executive summary. In the engagement described on the process page this is the surface probe of the Discover phase.

Why this exists

The chore it removes

Someone spends the first week clicking through the app, pasting URLs into a spreadsheet, hand-writing a playwright.config.ts from a blog post, inventing page objects with brittle CSS selectors, and wiring a CI workflow nobody trusts. Meanwhile the obvious defects — a 404 in the footer, a form nobody can tab through, a console full of red — go unrecorded because "we are still setting up".

→
What you get instead

One command. A crawl table per page (status, load time, console errors, failed requests, counts, h1, landmark), findings by severity with evidence JSON, a locator inventory with a confidence per element, a project you can npm test on the first run, and a report you can hand to the client — all traceable to a run id in the database.

The thesis behind this repo is that vendors' forward-deployed engineers deliver the AI and nobody independently measures what they delivered. Measurement needs a deterministic regression layer that exists before the pilot starts. This agent makes that layer exist on day one, from the running app alone, with no credentials beyond what a browser needs.

What this step does

See it in action

Run it & wire it in

You can run this yourself, end to end — every command below is real.

Before you start

  • Node 24 (the built-in node:sqlite driver needs it; npm test passes --experimental-sqlite).
  • A clone of the repo and npm install — this pulls Playwright, Fastify and zod; nothing else.
  • Any running web app you are allowed to crawl. The agent only follows same-origin links and never submits a form.

Step by step

  1. Install and fetch a browser
    npm install
npx playwright install chromium
    Why The crawler launches Chromium through Playwright. Only Chromium is needed for the agent itself; the generated project installs all three engines later with --with-deps.
    First run Done on 2026-09-11 while building the repo.
  2. Create the database
    npm run db:init
    Why Creates data/forward-qa.db with the engagements, runs, findings and artifacts tables (WAL mode, foreign keys on). Idempotent: every CREATE TABLE is IF NOT EXISTS, and every agent run calls the same schema on open anyway.
    Re-run Safe to repeat; nothing is dropped.
  3. Run it against a URL
    LLM_PROVIDER=none npm run agent:fdt -- --url https://app.example.test --org acme --max-pages 10

# behind basic auth, or with a session cookie
npm run agent:fdt -- --url https://staging.example.test --org acme --basic-user qa --basic-pass secret
npm run agent:fdt -- --url https://app.example.test --org acme --cookie "session=abc123" --cookie-domain app.example.test
    Why The CLI creates an engagement, runs the agent and prints the output JSON (pages_crawled, findings_by_severity, infra_dir, report_path, locators_total, summary) plus the run id. LLM_PROVIDER=none makes the run reproducible; leave it unset and the adapter probes for a local Ollama.
    First run 2026-09-11 04:32 against a local three-page site: 3 pages, 4 findings, 9 locators, 11 files, 2.0 s.
    Re-run A new run id, a new workspace/<run_id>/ directory and new rows; earlier runs are never modified.
  4. Read the report
    cat workspace/<run_id>/report.md
cat workspace/<run_id>/run.log
    Why report.md has the executive summary, the crawl table, broken links, findings by severity, the locator inventory per page (property, Playwright expression, confidence), the provisioned file list and five next steps. run.log has one timestamped line per phase and per visit.
  5. Run what it built
    cd workspace/<run_id>/infra
npm install
npx playwright install --with-deps
npm test
BASE_URL=https://staging.example.test npm test
    Why The smoke suite should be green on the first run against the same environment; a red test is either a real regression or one of the findings above. BASE_URL overrides the baked-in target so the same suite runs against staging.
    First run The demo run's /about test carries a NOTE instead of an h1 assertion because recon found no heading.
  6. Same thing through the REST API
    npm start   # http://localhost:8787
curl -s -X POST localhost:8787/engagements -H 'content-type: application/json' \
  -d '{"org":"acme","name":"first pass","target_url":"https://app.example.test"}'
curl -s -X POST localhost:8787/agents/forward-deployed-tester/runs -H 'content-type: application/json' \
  -d '{"engagement_id":"<id>","input":{"target_url":"https://app.example.test","org_slug":"acme","max_pages":10}}'
curl -s localhost:8787/agents/forward-deployed-tester/runs/<run_id>/report
    Why The run is synchronous: the POST returns { run, output } when the crawl is done. GET /runs/:id returns the run with its findings and artifacts; the report route serves report.md as text/markdown. Invalid input comes back as 400 with zod issues.
  7. Hand the MCP config to a client
    cd workspace/<run_id>/infra
cat .mcp.json
npm run mcp    # or let Claude Code / Cursor launch it from .mcp.json
    Why .mcp.json registers the Playwright MCP server with BASE_URL set to the crawled site. An MCP client can open the app, walk the page objects and write new specs; the README in the generated project lists three prompts to start with.
  8. Run the agent's own tests
    npm run typecheck
npm test
    Why 89 tests across both agents. For this one: locator derivation, findings rules, generators and report rendering run without a browser; integration.test.ts starts an in-process HTTP server and drives the real crawler through Chromium.
    First run 89 pass, 0 fail, 2.9 s on 2026-09-11.

What you give it

--url / target_url
Start page; the crawl never leaves its origin.
--org / org_slug
Letters, digits, - and _. Names the generated package (<org>-e2e) and the report.
--max-pages / max_pages
1–50, default 15. Rendered pages only.
--timeout-ms / timeout_ms
1000–120000, default 15000. Per navigation.
--basic-user + --basic-pass, or --cookie + --cookie-domain
Optional auth. Cookies are name=value;name2=value2; the domain defaults to the target host.
--headed, --no-mcp
Watch the browser; skip the MCP files.

What comes back

workspace/<run_id>/infra/
The provisioned Playwright + MCP project: 8 fixed files plus one page object per page.
workspace/<run_id>/report.md and report.json
Human and machine forms of the same report.
workspace/<run_id>/run.log
Timestamped phase and visit log.
Rows in runs, findings, artifacts
Queryable through GET /runs/:id, /runs/:id/findings, /runs/:id/artifacts.
Running it again. Nothing is cached and nothing is overwritten: every run gets a fresh run id, workspace directory and rows. Re-run after a deploy and diff the two report.json files — new broken links, new console errors and a changed locator inventory are the regression signal before the smoke suite even runs. Raise max_pages when the report says links were skipped.
Plug it into your stack. Commit workspace/<run_id>/infra into the application repository as its e2e/ folder; the included workflow runs on push, pull request, nightly and manual dispatch and uploads the HTML report. Point BASE_URL at each environment through repository variables. For the wider engagement, this run is the Discover-phase surface probe on the process page: its findings and the smoke suite are the baseline that later phases measure against. To add a probe of your own (an API probe, a log probe) follow the same shape — a pure derive*() function, rows through ctx.db, files through generateInfra-style string builders — and register it in src/api/server.ts.

Under the hood — for the curious

A slide for each moving part. Slide back and forth.

1 / 6

Queue and budgets

When it runs
Phase 1 of 4, once per run.
Takes in
target_url, max_pages, timeout_ms, headless, optional auth.
Shows out
A CrawlResult: rendered pages, brokenLinks, skipped URLs and durationMs — via crawl(), with normaliseUrl() and isCrawlable() guarding the queue.
2 / 6

In-page harvest

When it runs
Inside every successful visit, after load and up to 2 s of network idle.
Takes in
The live DOM, and maxElements = 60.
Shows out
A HarvestResult: title, h1, landmark flag, alt and label counts, element counts, same-origin link list and up to 60 ElementDescriptors — via HARVEST_SCRIPT, plain JavaScript evaluated by Playwright.
3 / 6

Locator derivation

When it runs
Back in Node, for every harvested descriptor.
Takes in
Tag, type, role, accessible name, label, placeholder, text, test id, id, name attribute, classes.
Shows out
A DerivedLocator with strategy, Playwright code and confidence, plus a unique camelCase property name — via deriveLocator(), toPropertyName() and uniqueNames().
4 / 6

Findings

When it runs
Phase 2, after the crawl, before anything is written.
Takes in
The CrawlResult.
Shows out
Rows in the findings table with severity, category, title, detail and evidence JSON — via deriveFindings() and Db.addFinding().
5 / 6

Provisioning and persistence

When it runs
Phases 3 and 4.
Takes in
The page records and the run options.
Shows out
11+ files under workspace/<run_id>/infra, one artifacts row each; report.md and report.json; run.log with a timestamp per line; the runs row marked succeeded with the output JSON — via generateInfra(), renderReportMarkdown(), buildReportJson() and executeAgent().
6 / 6

Optional local model

When it runs
Only in phase 4, only if a local server answers within 800 ms.
Takes in
The deterministic summary and a prompt that forbids new facts.
Shows out
A rephrased summary, or the original — via maybeLlm(); assertLocalEndpoint() rejects any host that is not loopback, RFC 1918 or .local unless LLM_ALLOW_REMOTE=1.
